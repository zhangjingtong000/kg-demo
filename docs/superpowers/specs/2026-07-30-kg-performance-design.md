# KG 独立性能与多尺度可视化设计

## 状态与目标

**状态：待用户审阅。**

本设计仅覆盖知识图谱的独立性能、规模适配与交互可读性。深空背景、产品 UI 和两者的渲染融合均明确后置，避免在 KG 的节点/边/相机模型尚未稳定时产生返工。

项目的答辩主画面必须保留当前 `web/index3d-bounce.html` 的液态玻璃节点、发光关系边、点击聚焦、悬停高亮、节点拖拽与回弹体验；同时应在节点与关系规模上升时，平稳切换到更轻量、更易理解的表现。

## 约束与性能基线

测试设备为搭载 RTX 4060（8GB 显存）、32GB 内存的桌面环境。默认答辩基线暂定为 Chrome、1920×1080、外接电源、独显工作；设备像素比 1 和 2 分别记录。

最终业务规模尚未固定，不能把某个模拟节点数当成产品承诺。基准器的目的，是测量当前引擎的性能曲线和 LOD 切换收益，再由真实文档抽取结果决定正式阈值。

以 60 FPS（16.7ms/帧）为目标，KG 独立阶段采用保守预算：

| 维度 | KG 独立阶段验收 | 最终整合阶段验收 |
|---|---|---|
| 常态帧时间 | P95 不高于 10ms | P95 不高于 16.7ms |
| 短时交互峰值 | P99 不高于 20ms | P99 不高于 25ms |
| 输入响应 | 选择、搜索与面板请求在 100ms 内有可见反馈 | 同左 |
| 长任务 | 不允许连续可见掉帧或主线程冻结 | 同左 |

独立阶段要求留下约 40% 的帧预算，供后续背景、毛玻璃 UI、标签、问答和运行环境占用。若 KG 独立运行已处在 60 FPS 临界值，则视为未通过。

## 当前实现的风险点

当前实现在 26 节点、55 边的展示规模下合适，但不能直接扩展：

1. 每条关系建立主光束与芯光束两套管状几何体，布局与拖拽时更新大量顶点缓冲。
2. 每个标签都是 CSS2D/DOM 元素；大规模下布局、绘制与重叠将成为主要瓶颈。
3. 当前默认态的节点、边和标签视觉权重接近，密集图会首先失去可读性，随后才是帧率。
4. 节点逐一创建 Mesh 的方式不适合全局展示数千实体。

## 多尺度展示策略

### 微观探索层（目标：精致、可解释）

面向约 20–80 个同时可见实体。保留当前高保真玻璃球、双层发光管线、完整聚焦与回弹交互。它是答辩主舞台，也是用户理解局部知识结构的模式。

### 中观社区层（目标：可浏览）

面向约 80–500 个实体。节点按类型和社区构成星团；节点尺寸、关系表现和标签密度按缩放降低。仅核心、选中、搜索命中与高中心性实体显示标签；默认边改为低成本细线，选择路径才升格为发光关系边。

### 宏观地图层（目标：可定位）

面向 500–5,000 个实体。默认展示社区聚合体、跨社区关系和少量代表节点，而非逐个实体。进入一个社区或搜索到实体后，才加载/展开中观或微观层。

### 超大规模策略（目标：不误导）

5,000 以上实体不承诺“完整逐点玻璃渲染”。系统以社区、类型、搜索与按需加载为主；GPU instancing 或 point sprites 只用于概览层。十万量级图需要单独的数据分片、聚合和查询方案，不属于当前视觉模式的直接扩容。

上述数字均为**待校准的性能档位**，不是由后端产出或产品需求预先决定的硬阈值。

## 基准器设计

新增独立的性能场景，不依赖真实 PDF 或 LLM：同一数据结构可生成不同节点数、边密度、社区数、标签密度和类型分布的确定性图数据。随机数使用固定种子，确保每次对比一致。

### 初始场景矩阵

| 场景 | 节点/边 | 社区结构 | 主要用途 |
|---|---:|---|---|
| Legacy | 26 / 55 | 当前健身数据 | 回归当前视觉与交互 |
| Local Dense | 80 / 320 | 4–6 个社区 | 微观模式压力与标签验证 |
| Community Browse | 250 / 1,200 | 12 个社区 | 中观模式、筛选与社区展开 |
| Macro Overview | 1,000 / 5,000 | 35 个社区 | 聚合图、搜索定位与 LOD 验证 |
| Stress Aggregate | 5,000 / 20,000 | 100 个社区 | 宏观聚合稳定性；不渲染全部高保真节点 |

### 交互场景

每个规模档位都记录：

1. 首屏创建与稳定帧时间；
2. 空闲自动旋转；
3. 旋转、缩放、平移；
4. 节点悬停与聚焦；
5. BFS 布局重排；
6. 拖动节点、更新相连边与回弹；
7. 标签密度变化；
8. 预留 UI 负载：固定侧栏骨架、标签层与面板动画，不接入正式背景。

每项记录 FPS 分位数、帧时间、首屏时间、长任务、JS 堆内存、WebGL 绘制调用数/几何体数量，以及用户可见的输入反馈时间。

## 实现边界与演进

第一轮不改动生产展示页，而是在独立实验入口中建立可重复的基准与数据生成器。通过基准后，再把验证过的抽象逐步迁回主 KG 页面。

优先优化顺序：

1. 数据与渲染表示分离；
2. 标签 LOD 与重叠控制；
3. 边表现 LOD：细线、发光线与高保真管线分级；
4. 节点表示 LOD：Mesh、instanced mesh、point sprite、社区聚合；
5. 交互只作用于可见/选中子图；
6. 最后才评估背景与 UI 融合后的总预算。

## 验证与后端校准

基准器完成后，使用短文档、典型论文/综述、长关系密集文档和含图片/表格 PDF 跑现有抽取管道。记录实际页数、分块数、实体数、关系数、类型分布、社区结构、抽取时长与错误。真实结果将决定：

- 默认进入哪个尺度层；
- 何时触发社区聚合；
- 答辩主文档的选择；
- 后端需要支持的分页、社区和证据字段。

## 非目标

- 本阶段不融合 `assets/deep-space-galaxy.html`。
- 本阶段不重写 FastAPI、LLM 抽取或 Neo4j 持久化。
- 本阶段不以十万节点的逐实体高保真渲染作为目标。
