# KG 性能测试协议

## 目的

回答两个独立问题：

1. 当前成品 KG 在加入产品 UI 后是否仍然流畅；
2. 当可见节点、关系和标签数量上升时，当前高保真表现在哪个规模开始不再适合直接使用。

这不是“替代场景”的性能测试。正式数据只能来自复用 `web/index3d-bounce.html` 的节点着色、双层关系边、CSS2D 标签、BFS 聚焦重排、拖拽传播与回弹逻辑的页面。

## 明确禁止

- 不以独立写出的近似 Three.js 场景代替真实 KG 页面。
- 不把模拟焦点动画的结果写进成品性能结论。
- 不把运行于集成显卡、软件渲染器或未确认 GPU 的数据写进正式报告。
- 不在改变节点数的同时改变边密度、标签策略、分辨率、DPR 或交互脚本。
- 不只报告平均 FPS；平均值掩盖卡顿时，该结果无效。

## 固定测试环境

| 项 | 正式基线 |
|---|---|
| 设备 | RTX 4060 Laptop GPU（8GB）、32GB 内存 |
| 浏览器 | 记录实际 Chrome 完整版本 |
| 图形适配器 | WebGL 调试信息必须显示 NVIDIA GeForce RTX 4060 Laptop GPU |
| 视口 | 1920 × 1080 CSS 像素 |
| DPR | 1、2 分开测试 |
| 电源 | 外接电源、高性能电源模式 |
| 页面状态 | 单一被测页；关闭或记录其他高负载应用 |
| 运行方式 | 每次独立加载页面；首轮仅用于预热，不进入统计 |

所有结果以毫秒判断；显示器刷新率只作为背景信息记录，不以“FPS 很高”掩盖长帧。

## 两层性能口径

### Clean ceiling（当前可执行）

仅加载真实 KG 页面，记录在**固定实际桌面环境**下的 KG 性能上限。浏览器、GPU、DPR、视口、数据集与交互脚本必须在同一浏览器会话中成对运行；此数据不得用于宣称“加入背景与 UI 后仍流畅”。

每项运行前、运行中、运行后都必须记录 10 秒环境快照：全机 CPU 利用率、可用内存、前台/后台进程的 CPU 增量与工作集、GPU Engine 的非测试进程峰值。测试浏览器、DWM、Codex/ChatGPT、WebView、即时通讯软件和系统服务均属于环境的一部分，不得凭空忽略或删除。若运行前后任一项发生显著漂移（例如新出现高负载进程、总 CPU 或非测试 GPU 负载发生异常尖峰），该次样本标记为无效并重跑。

### Defense budget（产品壳完成后执行）

在同一真实页面中启用固定构图的深空背景、真实侧栏/UI 壳和真实状态层后重跑。该层才是答辩性能结论；禁止以任意第三方程序或随机 CPU/GPU 压力代替产品组件，因为那样不可复现且不代表产品成本。

## 真实页面测试档位

在完全相同的高保真渲染与交互下准备以下固定数据集。节点、边和标签均为可见实体；同一档位使用固定 seed，确保布局和关系一致。

| 档位 | 节点 | 关系 | 标签 | 用途 |
|---|---:|---:|---:|---|
| S0 | 26 | 65 | 26 | 当前成品回归基线 |
| S1 | 50 | 105 | 50 | 小幅扩展 |
| S2 | 80 | 175 | 80 | 高保真微观层上限候选 |
| S3 | 120 | 270 | 120 | 失效拐点探测 |
| S4 | 200 | 460 | 200 | 高保真模式不适用的证据 |

关系密度约保持在每节点 5.1 条关系，并保留连通主干、局部簇和跨簇关系。除数量与固定数据内容外，所有渲染与交互逻辑相同。

## 固定交互脚本

每个档位至少执行以下场景。脚本只能调用页面真实的用户路径：鼠标事件触发节点命中、真实 `bfs()`、真实 `radialLayout()`、真实边刷新与真实标签更新。

| 编号 | 场景 | 采集区间 |
|---|---|---|
| A | 空闲展示 | 稳定 10 秒 |
| B | 相机旋转 | 固定 6 秒拖拽轨迹后稳定 4 秒 |
| C | 聚焦重排 | 点击固定高连接度节点起，至节点位置与关系边稳定 |
| D | 取消聚焦 | 点击空白处起，至原布局稳定 |
| E | 拖拽与回弹 | 固定距离拖动节点、松开，至回弹稳定 |
| F | UI 预留 | 在 S0、S2 上逐层启用侧栏预留和静态 UI 骨架；KG 必须平移让位 |

`radialLayout()` 的扰动在正式测试模式下由固定 seed 提供；默认展示模式仍保留当前自然随机效果。

## 采集指标

每个场景记录：

- P50、P95、P99、最大帧时间与超过 16.7ms / 33.3ms 的帧比例；
- 首屏第一次绘制、点击到首个视觉响应、点击到重排/回弹稳定的时间；
- Long Task 数量和持续时间；
- WebGL draw calls、几何体、纹理数；
- 标签数、节点数、边数、DPR、视口、浏览器版本、实际 GPU；
- Chrome Performance Trace，用于定位主线程、CSS2D/布局、边几何更新和 GPU 负载。

正式矩阵分两阶段，以避免在已知不适合的 S3/S4 上浪费 UI 与 DPR 2 的测量时间：

1. **规模扫描**：S0–S4 在 DPR 1 下运行 A（空闲）、C（聚焦重排）、E（拖拽回弹）；
2. **答辩候选扫描**：S0、S2 在 DPR 2 下运行 A–E；S0、S2 在 DPR 1 与 2 下运行 F（UI 预留）。

每个“档位 × 场景 × DPR”独立运行 6 次：第 1 次预热丢弃，后 5 次记录中位数和最差值。任何环境不满足固定条件的运行均标记为无效，不能和正式结果合并。

## 通过线与结论规则

### 当前答辩成品（S0，包含 UI 预留）

- 空闲与相机交互：P95 ≤ 16.7ms，P99 ≤ 25ms；
- 聚焦、取消聚焦、拖拽/回弹：超过 33.3ms 的帧不得连续出现，且交互开始后 100ms 内出现可见反馈；
- 无超过 100ms 的主线程冻结。

### 规模结论

某档位只有在全部 A–E 场景满足上述“不卡顿线”时，才可称作该高保真模式的安全可见规模。第一个持续失败的档位不是“需要再优化一下”的模糊结论，而是切换标签 LOD、边 LOD、社区聚合的证据。

## 分层融合顺序

1. 先完成 S0–S4 的纯 KG 数据；
2. 仅在 S0、S2 上加 UI 预留，计算 UI 成本；
3. 再叠加固定构图的深空背景，计算背景成本；
4. 最后记录完整答辩场景总预算。

## 旧数据处理

`web/benchmark/` 中的独立近似场景仅作开发草稿。此前从该页面获得的任何数值、以及错误运行于 Intel 核显的自动化结果，均不得进入正式性能报告。
